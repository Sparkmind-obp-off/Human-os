# KAEVOS — DATA MODEL AND D1 SCHEMA

**Version:** 1.0  
**Status:** DATA MODEL BASELINE — IMPLEMENTATION READY  
**Brand:** KAEVOS  
**Underlying system:** Human-OS  
**Runtime:** Cloudflare Workers  
**Database:** Cloudflare D1 (SQLite)  
**Related contracts:** `34_KAEVOS_OPERATING_ARCHITECTURE.md`, `35_KAEVOS_API_CONTRACT_SPECIFICATION.md`

---

## 1. Purpose

This document defines the minimal production-minded relational data model for KAEVOS V0.

The model must support the operating loop:

**COMMAND → INTENT → PLAN → PERMISSION → CONFIRMATION → EXECUTION → VERIFICATION → RESULT → AUDIT**

The schema is intentionally small. KAEVOS must not turn D1 into a warehouse for every external payload.

### Primary goals

- persist command lifecycle state;
- preserve execution traceability;
- support idempotent API submission;
- record connector and provider operational events;
- preserve human permission/confirmation decisions;
- support audit queries and cursor pagination;
- keep external systems authoritative for their domain data;
- keep secrets out of D1;
- remain compatible with Cloudflare D1/SQLite.

### Non-goals for V0

- full analytics warehouse;
- permanent storage of raw LLM conversations;
- permanent storage of complete third-party API responses;
- storing payment credentials;
- replacing Duitku, GitHub, Cloudflare, TikTok, Shopee, or other systems of record;
- premature multi-tenant complexity.

---

## 2. Data Ownership Principle

KAEVOS stores **operational state**, not ownership of external domain truth.

| Data | Authority |
|---|---|
| Command lifecycle | KAEVOS |
| Execution lifecycle | KAEVOS |
| Permission decision | KAEVOS policy/audit |
| Confirmation record | KAEVOS |
| Connector health metadata | KAEVOS, based on latest observed check |
| Payment transaction truth | Duitku |
| GitHub repository/file truth | GitHub |
| Cloudflare deployment truth | Cloudflare |
| KAEVAX commercial domain truth | KAEVAX domain layer |
| LLM model output | Provider, with only sanitized KAEVOS metadata persisted by default |

KAEVOS may cache or normalize external data for an operational result, but such data must be clearly treated as an observation/cache rather than authoritative ownership.

## 3. D1 Architecture

### 3.1 Database

Use one D1 database for the initial KAEVOS environment.

Recommended binding:

```
DB
```

Environment-specific databases are preferred over mixing production and development data.

### 3.2 SQLite compatibility

The schema must remain compatible with SQLite/D1:

- `TEXT`
- `INTEGER`
- `REAL`
- `BLOB` only when genuinely required

Use ISO-8601 UTC timestamps as `TEXT`.

Example:

```
2026-09-19T04:00:00.000Z
```

### 3.3 Identifier convention

Use opaque string IDs generated by the application.

Recommended format:

```
cmd_<unique>
run_<unique>
step_<unique>
con_<unique>
aud_<unique>
prv_<unique>
cnf_<unique>
idem_<unique>
ses_<unique>
```

The exact ID generator may be UUID/ULID based, but the application must use one consistent implementation.

Do not expose sequential database row IDs as public resource identifiers.

### 3.4 Foreign keys

Enable foreign-key enforcement on every database connection/session where supported by the runtime.

Logical relationships must be enforced with foreign keys where practical.

Deletion should normally use explicit lifecycle/retention policies rather than cascading destructive deletes across the audit trail.

# 17. State and Enum Rules

SQLite does not provide native enums suitable for this architecture.

Use `TEXT` plus application validation and, where stable enough, database `CHECK` constraints.

Example:

```CHECK (
  state IN (
    'RECEIVED',
    'UNDERSTANDING',
    'PLANNING',
    'AWAITING_CONFIRMATION',
    'EXECUTING',
    'VERIFYING',
    'COMPLETED',
    'FAILED',
    'REQUIRES_REVIEW',
    'CANCELLED'
  )
)
```

The authoritative transition rules remain in application code.

### Verification states

```
verified
partially_verified
unverified
verification_failed
not_applicable
```

### Risk classes

```
read_only
low_risk
consequential
destructive
financial
```

Exact policy mapping belongs in the security/permission specification.

# 18. Command State Transition Persistence

Every transition must be persisted atomically with the state-changing operation whenever practical.

Example:

```
RECEIVED
  ↓
UNDERSTANDING
  ↓
PLANNING
  ↓
AWAITING_CONFIRMATION
  ↓
EXECUTING
  ↓
VERIFYING
  ↓
COMPLETED
```

Failure:

```
ANY STATE
  ↓
FAILED
  ↓
REQUIRES_REVIEW
```

Cancellation:

```
PLANNING / AWAITING_CONFIRMATION / EXECUTING
  ↓
CANCELLED
```

The database must never be used to infer that a state transition is valid merely because both states are stored values.

# 19. Transaction and Consistency Rules

D1 transactions should protect small state transitions.

### Example: starting a run

The transaction should, as one logical unit:

1. verify the command is executable;
2. create the execution run;
3. create its steps;
4. update command state to `EXECUTING`;
5. append the corresponding audit event.

If any required write fails, the transaction should roll back.

### External calls

Do not hold a database transaction open while waiting on a slow external API.

Instead:

1. persist intent/state;
2. commit;
3. perform external operation;
4. persist result;
5. verify;
6. finalize state and audit.

This avoids long-lived locks and improves resilience.

### External side effects

Database atomicity cannot roll back an already completed external side effect.

Therefore:

> **Idempotency + external verification + explicit retry policy are required for side-effecting connectors.**

# 20. Optimistic Concurrency

KAEVOS must prevent stale command updates.

V0 may use `updated_at` as a lightweight optimistic concurrency signal.

For stronger protection, add an integer:

```
revision INTEGER NOT NULL DEFAULT 1
```

and update with:

```
UPDATE commands
SET state = ?, revision = revision + 1, updated_at = ?
WHERE id = ? AND revision = ?
```

If zero rows are updated, the caller has a stale view and must reload.

### Recommended V0 decision

Use `revision` on `commands` and `execution_runs`.

Do not introduce distributed locks before actual concurrency requirements justify them.

---

# 21. Cursor Pagination

Large histories must use cursor pagination.

For a stable query ordered by:

```
created_at DESC, id DESC
```

the cursor can encode:

```
{
  "created_at": "...",
  "id": "aud_..."
}
```

The next query uses the tuple as a boundary rather than OFFSET.

Example concept:

```sql
WHERE
  (created_at < ?)
  OR (created_at = ? AND id < ?)
ORDER BY created_at DESC, id DESC
LIMIT ?
```

The API cursor should be opaque to clients.

Never trust arbitrary cursor fields without validation.

# 22. Sensitive Data Rules

## Never store in D1

- API keys
- access tokens
- refresh tokens
- private keys
- passwords
- payment credentials
- webhook signing secrets
- authorization headers
- raw cookies
- full sensitive provider payloads

## Minimize

- user-provided private content;
- payment/customer personal data;
- raw external responses;
- raw model prompts/responses;
- detailed infrastructure metadata.

## Logs and audit

Audit summaries must be useful but sanitized.

Example allowed:

```
Duitku transaction read completed; 12 records normalized.
```

Avoid:

```
Authorization: Bearer <token>
```

or dumping an entire customer/payment payload.

# 23. JSON Storage Rules

JSON is appropriate for bounded, evolving structures such as:

- normalized intent;
- capability lists;
- small plans;
- safe metadata;
- normalized result fragments;
- session context.

JSON is not a substitute for relational columns when KAEVOS needs to:

- filter frequently;
- sort frequently;
- enforce uniqueness;
- join operational records;
- paginate.

### Size rule

All JSON fields must have application-level maximum sizes.

Reject or truncate unsafe/unbounded diagnostic payloads before persistence.

Never silently truncate data required for correctness.

# 24. Retention and Data Lifecycle

V0 should define retention before production use.

Recommended baseline:

| Data | Suggested default |
|---|---|
| commands | 90–180 days |
| execution_runs | 90–180 days |
| execution_steps | 90–180 days |
| connector_events | 30–90 days |
| provider_events | 30–90 days |
| sessions/context | 30–90 days |
| idempotency_keys | 24–72 hours, based on API policy |
| connector_registrations | current state; historical changes via audit |
| audit_events | longer retention, e.g. 180–365 days, subject to business/legal requirements |
| confirmations | aligned with command/audit retention |

These are engineering defaults, not legal retention advice. Financial, contractual, tax, privacy, or regulatory requirements may require different retention.

### Deletion principle

Delete dependent operational data in a controlled order.

Preserve required audit records until their retention policy expires.

Do not implement blanket `DELETE FROM *` cleanup jobs.

---

# 25. External Data Cache Policy

If KAEVOS stores an observation from an external system:

- record the source connector;
- record observation time;
- retain external reference where useful;
- treat the external platform as authoritative;
- do not present stale cached data as live truth.

Example:

```
source = duitku
observed_at = 2026-09-19T04:10:00.000Z
```

A future revenue view may use cached normalized records, but must clearly define freshness.

# 26. Migration Strategy

Use numbered forward-only migrations.

Recommended:

```
src/db/migrations/
  0001_initial_schema.sql
  0002_add_command_revision.sql
  0003_add_retention_fields.sql
```

Each migration must:

1. have a unique number;
2. be committed to source control;
3. be deterministic;
4. be safe to apply once;
5. avoid destructive changes unless explicitly reviewed;
6. be tested against a fresh D1 database;
7. be tested against a representative existing database before production rollout.

Do not edit an already-applied migration to change production history.

Create a new migration instead.

# 27. Initial D1 Migration

The following is the baseline schema direction for V0.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY,
  actor_id TEXT NOT NULL,
  channel TEXT NOT NULL CHECK (channel IN ('text','voice','api')),
  title TEXT,
  context_json TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  expires_at TEXT
);

CREATE INDEX IF NOT EXISTS idx_sessions_actor_updated
  ON sessions(actor_id, updated_at DESC);

CREATE TABLE IF NOT EXISTS commands (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  request_id TEXT,
  actor_id TEXT NOT NULL,
  input_type TEXT NOT NULL CHECK (input_type IN ('text','voice_transcript','api')),
  input_text TEXT,
  intent_name TEXT,
  intent_json TEXT,
  plan_id TEXT,
  plan_version INTEGER,
  state TEXT NOT NULL CHECK (
    state IN (
      'RECEIVED','UNDERSTANDING','PLANNING',
      'AWAITING_CONFIRMATION','EXECUTING','VERIFYING',
      'COMPLETED','FAILED','REQUIRES_REVIEW','CANCELLED'
    )
  ),
  result_status TEXT,
  verification_status TEXT,
  failure_code TEXT,
  failure_message TEXT,
  revision INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  completed_at TEXT,
  expires_at TEXT,
  FOREIGN KEY (session_id) REFERENCES sessions(id)
);

CREATE INDEX IF NOT EXISTS idx_commands_state_updated
  ON commands(state, updated_at DESC);

CREATE INDEX IF NOT EXISTS idx_commands_actor_created
  ON commands(actor_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_commands_session_created
  ON commands(session_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_commands_request_id
  ON commands(request_id);

CREATE TABLE IF NOT EXISTS execution_runs (
  id TEXT PRIMARY KEY,
  command_id TEXT NOT NULL,
  plan_id TEXT NOT NULL,
  plan_version INTEGER NOT NULL,
  state TEXT NOT NULL CHECK (
    state IN (
      'PENDING','EXECUTING','VERIFYING',
      'COMPLETED','FAILED','REQUIRES_REVIEW','CANCELLED'
    )
  ),
```

# 28. Foreign-Key Deletion Policy

Do not default all relationships to `ON DELETE CASCADE`.

Reason: operational and audit history must not disappear unexpectedly because a parent record is removed.

Recommended approach:

- operational rows expire through retention jobs;
- audit rows have their own retention lifecycle;
- application deletion operations are explicit;
- connector registration removal should normally be a state change to `disabled`, not physical deletion.

If physical deletion is required later, define it in a dedicated migration and retention design.

# 31. Audit Trace

A complete trace should be reconstructable through:

```
request_id
   ↓
command_id
   ↓
plan_id + plan_version
   ↓
run_id
   ↓
step_id
   ↓
connector_event
   ↓
verification
   ↓
audit_event
```

The audit trail must answer:

- which actor initiated the command;
- which intent was resolved;
- which plan version was executed;
- which permission decision was made;
- whether confirmation was required;
- which connector operation occurred;
- what external reference was returned;
- whether verification succeeded;
- what final state was recorded.

# 32. Idempotency Lifecycle

Recommended flow:

```
Request arrives
    ↓
Validate Idempotency-Key
    ↓
Hash normalized request
    ↓
Lookup (actor_id, key)
    ↓
No record ──→ create command + idempotency record
    │
    └── existing
          ├── same hash → return existing command/result
          └── different hash → IDEMPOTENCY_CONFLICT
```

The idempotency record and command creation should occur in the same database transaction.

Retention of idempotency records must cover the client retry window.

---

# 33. Confirmation Integrity

Confirmation must be bound to:

```
actor_id
command_id
plan_id
plan_version
```

Before execution, KAEVOS must verify:

1. confirmation exists;
2. status is approved;
3. approval has not expired;
4. actor is authorized;
5. current plan ID matches;
6. current plan version matches;
7. plan has not materially changed.

If any check fails:

```
PERMISSION_REQUIRED
```

or an appropriate conflict error must be returned.

---

# 34. Verification Persistence

KAEVOS must distinguish:

```
Requested
Attempted
Completed
Verified
```

Database state examples:

### Read-only retrieval

```
run.state = COMPLETED
run.verification_status = verified
```

### External call succeeded but no verification available

```
run.state = COMPLETED
run.verification_status = unverified
```

### Action completed but follow-up verification contradicts the expected state

```
run.state = REQUIRES_REVIEW
run.verification_status = verification_failed
```

Never convert an unavailable verification into `verified`.

# 35. Financial Data Boundary

For Duitku and future payment connectors:

- transaction truth remains in Duitku;
- KAEVOS stores only the minimum normalized operational information needed;
- financial writes use stronger permission and verification;
- payment credentials never enter D1;
- webhook authenticity must be verified before events affect trusted state;
- financial reporting should include an observation timestamp/freshness indicator when relevant.

V0 should not create a complete accounting ledger unless the business requirements explicitly demand one.

---

# 36. Performance Constraints

V0 should optimize for predictable small queries.

Guidelines:

- use indexed lookups for command retrieval;
- keep JSON payloads bounded;
- avoid unbounded joins on every command request;
- avoid N+1 queries for execution traces;
- paginate audit histories;
- avoid storing large raw payloads;
- keep transactions short;
- do not perform external network calls inside D1 transactions.

If a query becomes a hot path, inspect query plans before adding infrastructure.

---

# 37. Backup and Recovery Expectations

D1 backup/restore behavior must be treated as an operational dependency, not assumed to be equivalent to a traditional self-managed SQLite backup.

Production deployment must document the currently supported Cloudflare D1 backup, Time Travel, export, and recovery capabilities available to the selected Cloudflare plan/environment.

Minimum operational requirements:

1. know how to recover production data;
2. know the retention window available;
3. document recovery ownership;
4. test recovery procedures periodically;
5. keep migrations in Git;
6. avoid relying on an undocumented manual database state.

Do not claim a specific backup SLA or retention period without verifying the current Cloudflare product terms/configuration.

# 39. Security and Privacy Controls

The database layer must enforce:

- parameterized queries;
- input validation;
- bounded JSON;
- secret exclusion;
- append-only audit behavior;
- authorization before reads;
- authorization before mutations;
- sanitized error persistence;
- retention policies;
- controlled administrative access.

The database repository layer must not become a way for an LLM or connector response to execute arbitrary SQL.

External content remains untrusted data.

# 40. V0 Scope Decision

The following are deliberately excluded from the initial schema:

- full user/organization multi-tenancy model;
- vector database;

- event-sourcing framework;
- accounting ledger;
- data warehouse;
- generic workflow-definition database;
- distributed lock service;
- separate cache database;

These may become valid later requirements, but they are not prerequisites for proving the KAEVOS command loop.

# 43. Architectural Invariants

1. D1 stores KAEVOS operational state, not universal external-system truth.
2. Secrets never enter D1.
3. Raw LLM prompts/responses are not persisted by default.
4. External API responses are untrusted input.
5. Command state transitions are enforced server-side.
6. Consequential actions remain traceable.
7. Confirmation is bound to an exact plan version.
8. Idempotency protects retry-sensitive command submission.
9. Completed and verified remain distinct.
10. Audit history is append-oriented.
11. External side effects cannot be rolled back by a D1 transaction.
12. Retries require an idempotency/safety strategy.
13. JSON remains bounded and purposeful.
14. V0 avoids unnecessary data infrastructure.
15. KAEVAX remains the commercial domain layer.
16. KAEVOS remains the single operating gateway.
